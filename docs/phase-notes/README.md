# 阶段结论文档（Phase Notes）

每个阶段完成后写一份，替代"凭记忆口述"。下一阶段的实施者（人或 agent）只读这一份，
就该知道：哪些结论已成定局、哪些坑不能重踩、哪些约束必须照做。

## 位置与命名

```
docs/phase-notes/
├─ README.md            # 本文件：约定 + 索引
├─ _TEMPLATE.md         # 模板，复制后改名填写
├─ P0-spike.md          # 阶段号与 PORTING_PLAN.md 的阶段表一致
├─ P1-abstraction.md
└─ …
```

文件名固定为 `<阶段号>-<主题>.md`，**阶段号必须与 `PORTING_PLAN.md` §2 阶段总览一致**，
主题用两三个词概括该阶段的产出（如 `spike`、`abstraction`、`shell`、`list`）。

## 必须有这七段（顺序固定）

| # | 段 | 写什么 |
|---|---|---|
| 1 | **元信息** | 阶段号 / 日期区间 / 环境（OS、SDK、关键依赖版本）/ 一句话结论 |
| 2 | **结论速览** | 表：验证项 \| 结论等级 \| 对计划的影响。只写结论，不展开 |
| 3 | **逐项详述** | 每项：怎么验的 → 原始证据 → 结论 → 踩到的坑。证据要能指到具体行 |
| 4 | **风险联动** | 表：风险号 \| 变化（↑上调 / ↓下调 / ✚新增 / ✖消失）\| 理由 |
| 5 | **对下一阶段的硬约束** | 照做清单。写成命令式短句，不解释也行 |
| 6 | **遗留项（分级）** | 🟥 阻断 / 🟨 可延后 / ⬜ 观察，各列具体条目与归属阶段 |
| 7 | **附：实测证据** | 原始日志、命令输出、截图路径。注明"某次运行样例，数值随环境浮动" |

## 两套分级

**结论等级**（用于第 2 段每一条验证项）

| 等级 | 含义 |
|---|---|
| ✅ **通过** | 达成本阶段通过标准，无需改写法 |
| 🟡 **有条件通过** | 能跑，但必须换一种写法/配置；务必把"改法"写进第 5 段 |
| ⛔ **否决** | 路线不通，走计划里的退路；同时必须回来改计划 |

**问题分级**（用于第 3、6 段的每条发现）

| 级别 | 判据 |
|---|---|
| **A · 阻断** | 不解决，下一阶段无法开工 |
| **B · 工时** | 会浪费 ≥ 半天；不改也能往前走 |
| **C · 打磨** | 体验、美观、可选优化 |

## 硬规矩

1. **结论必须有原始证据支撑。** 写"通过"就要能指出日志里的哪一行；没有证据的结论一律标 🟡。
2. **notes 与计划冲突时，以 notes 为准，并当天改 `PORTING_PLAN.md`**（不许留下两份互相矛盾的文档）。
3. **只写结论 + 证据 + 约束**，不写心路历程、不写"我试了三次才明白"。
4. **notes 与当阶段代码进同一个提交**，不后补——阶段结束时它是交付物的一部分。
5. 数字（性能、耗时、体积）标注测量条件；换机器会变，别当成绝对阈值。
